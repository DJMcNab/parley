# Phase Three Implementation Plan — Apple emoji rendered metrically-compatible with Noto Color Emoji

## 1. Overview / goal

Build `examples/apple_emoji/phase_three` as a copy-and-extend of phase_two. Instead of
sizing each emoji inline box to the **Apple** system advance, we size it to the **Noto
Color Emoji** advance, and we scale the captured Apple emoji pixels linearly so their
rendered advance matches Noto. The result *looks like* Apple emoji but *measures like* Noto
Color Emoji.

The browser app must download/embed **as little Noto data as possible** — never the 25 MB
font. We achieve this by generating, with a native build-time tool, a tiny table of
`codepoint → advance` for Noto Color Emoji and embedding only that table in the wasm app.

Validation compares the Parley layout line width to the same string measured in-page with
the **real** Noto Color Emoji font (served *only* for the validation reference, kept out of
the app's own load path), tolerance ~1 px.

Vertical alignment / baselines are explicitly **out of scope** this phase (carried over
from phase_two behaviour; do not regress it, but do not tune it).

**Constraints honored:** no Apple emoji font embedded/served; the full Noto font is never in
the production load path (only a small generated table is embedded); no Parley library
changes; nothing committed.

## 2. Verified facts about NotoColorEmoji-Regular.ttf

Probed with `fonttools` on `parley_dev/assets/fonts/noto_color_emoji/NotoColorEmoji-Regular.ttf`:

- **unitsPerEm (upem) = 1024.**
- **numGlyphs = 41863**; **cmap entries = 1499** (codepoints `0x20`..`0xFE837`).
- **Advance distribution is essentially binary:** of the 1499 cmapped codepoints,
  **1461 have advance = 1275** font units and 38 have advance = 0 (variation selectors,
  ZWJ, combining marks, etc.). Across *all* glyphs: 41825 = 1275, 38 = 0.
- Our two example emoji resolve to single glyphs with advance **1275**:
  - `😀` U+1F600 → glyph `u1F600`, advance **1275**.
  - `🎉` U+1F389 → glyph `u1F389`, advance **1275**.
- Therefore Noto advance in px = `1275 / 1024 * font_size`. At `font_size = 48`:
  **1275/1024 × 48 = 59.766 px** for each emoji.

Implication: for our single-`char` emoji, `codepoint → advance` fully determines the box
width; we never need to ship Noto's cmap or hmtx at runtime, only the resolved table.

## 3. Data-file design

### 3.1 What the file contains
A sorted table mapping **Unicode scalar value → advance in font units (u16)**, plus the
constant **upem = 1024**. Generated by resolving, at build time, every cmap entry through
Noto's cmap+hmtx (`glyph = cmap(cp)`, `advance = hmtx.advance(glyph)`). This is equivalent
to "the advance width of every glyph" (PLAN §Phase Three) but pre-resolved by codepoint so
the runtime needs no cmap.

- ~1499 entries × (u32 codepoint + u16 advance) ≈ **~9 KB** of raw data.
- (Because advances are near-constant we *could* store only the 38 exceptions + a default of
  1275, shrinking to <1 KB — noted as an optional optimization, but the full 1499-entry
  table is trivially small and simpler/robust, so ship the full table.)

### 3.2 File format — generated `.rs` (recommended)
Emit a generated Rust source file that the wasm crate `include!`s, so there is **zero
runtime download** and the payload cost is only the compiled table:

```rust
// GENERATED by noto_advance_gen — do not edit. (uncommitted)
pub const NOTO_UPEM: u16 = 1024;
/// (codepoint, advance_in_font_units), sorted ascending by codepoint.
pub const NOTO_ADVANCES: &[(u32, u16)] = &[
    (0x20, 651),
    /* … */
    (0x1F389, 1275),
    (0x1F600, 1275),
    /* … */
];
```

Runtime lookup is a `binary_search_by_key` on the slice. (Alternative formats — a compact
little-endian binary blob consumed via `include_bytes!` + manual parse, or JSON — work too,
but the generated `.rs` slice is the least code and matches the repo's "generated Rust
module" precedent in `parley_data_gen`. Pick the `.rs` slice unless build time is a concern.)

### 3.3 The generator — where it lives and how it runs
Precedent: `parley_data_gen` is a native `publish = false` bin that takes an output dir and
writes generated Rust into the tree (`main.rs` CLI + `lib.rs` `generate()`), using
`icu_*`/`packtab`. We mirror that shape but much smaller, using `skrifa`/`read-fonts`
(both already workspace deps: `skrifa = 0.43.2`, `read-fonts = 0.40.0`).

Recommended: a **separate tiny native crate** at
`examples/apple_emoji/phase_three/noto_advance_gen/` (its own `Cargo.toml`, `publish = false`).
Reasons:
- Keeps native-only deps (`skrifa`, `std::fs`) out of the wasm crate's dependency/feature
  set (the wasm crate builds for `wasm32-unknown-unknown` via trunk; a native `[[bin]]`
  sharing the same `Cargo.toml` risks pulling native-only code/features into the wasm build
  and complicates trunk).
- Run it once locally: `cargo run -p noto_advance_gen -- <out.rs>`.

Generator logic (skrifa):
```rust
use skrifa::{FontRef, MetadataProvider};
use skrifa::raw::TableProvider; // hmtx/head
let bytes = std::fs::read(NOTO_PATH)?;                 // repo path to NotoColorEmoji-Regular.ttf
let font = FontRef::new(&bytes)?;
let upem = font.head()?.units_per_em();                // 1024
let cmap = font.charmap();                             // MetadataProvider::charmap
let hmtx = font.hmtx()?;
let mut rows: Vec<(u32,u16)> = Vec::new();
for cp in 0u32..=0x10FFFF { if let Some(gid) = cmap.map(cp) {
    let adv = hmtx.advance(gid).unwrap_or(0);          // font units
    rows.push((cp, adv));
}}
rows.sort_by_key(|r| r.0);
// write NOTO_UPEM + NOTO_ADVANCES slice to the out path
```
(Confirm exact skrifa API names at implementation time — `charmap()`/`Charmap::map`,
`hmtx()`/`advance(GlyphId)`, `head()?.units_per_em()` are the expected 0.43 surfaces;
iterating the charmap's mappings directly instead of scanning 0..=0x10FFFF is a fine
alternative.)

Alternative if a second crate is unwanted: an `xtask` subcommand (the `xtask` crate is a
workspace member) — same code, invoked `cargo run -p xtask -- gen-noto-advances`. Either is
acceptable; the standalone crate is cleaner isolation. **Neither the generator nor its
output is committed.**

## 5. Runtime changes vs phase_two

Phase_two: `inline_box.width = apple_advance` (from `measureText`), blit maps capture→dest
at scale `1/S` (S = supersample/dpr), no horizontal stretch.

Phase_three changes (small, localized):

1. **Box width — `layout.rs`.** For each emoji at codepoint `cp`:
   ```rust
   let noto_units = noto_advance_units(cp).expect("emoji covered by Noto");
   let noto_px = noto_units as f32 / NOTO_UPEM as f32 * FONT_SIZE;  // e.g. 59.766 @48
   push_inline_box(InlineBox { width: noto_px, /* height as phase_two */, .. });
   ```
   where `noto_advance_units` binary-searches `NOTO_ADVANCES`. Keep the Apple `measureText`
   advance too (still captured in `capture.rs`) — we need it as the *source* denominator for
   the scale factor.

2. **Pixel scale factor — `render.rs` blit.** Compute
   `scale = noto_px / apple_advance_px` per emoji. Apply it **uniformly** (both axes, to
   preserve aspect ratio — "scale each Apple emoji linearly") on top of the existing `1/S`
   capture downscale. Concretely, in phase_two's destination-space sampling loop the source
   sample for dest pixel `(dx,dy)` becomes:
   ```
   sx = origin_x + (dx - dev_left_x) * S / scale
   sy = origin_y + (dy - dev_baseline_y) * S / scale
   ```
   i.e. the emoji ink now spans `apple_ink_width * scale` px and its advance box is the Noto
   width. Iterate dest pixels over the scaled ink bbox; nearest or bilinear sample. Since
   `scale ≈ 59.77 / apple_advance` and Apple's advance at 48px is typically ~57–58px, scale
   is ~1.03 — a mild uniform enlargement.
   - Horizontal anchor: keep the capture origin column mapped to the box left (`dev_left_x`),
     as phase_two. The scaled emoji may slightly exceed the box on the right if Apple ink
     overhangs; acceptable (advance is what we validate, not ink).
   - Vertical: keep phase_two's baseline mapping unchanged (baselines out of scope). The
     uniform vertical scale shifts ink height slightly; do not tune.

3. **New module `noto_advances.rs`** — generated; `include!`d or declared `mod`.

No other changes: segmentation, capture, vello_cpu pipeline, canvas presentation identical
to phase_two (copy verbatim).

## 6. Validation design

Goal: the total Parley layout line width equals the same string laid out with **real** Noto
Color Emoji advances (Latin from Arimo, emoji from Noto), within ~1 px, while the pixels
drawn are scaled Apple emoji.

### 6.1 In-page real-Noto reference (measurement only)
- Declare a validation-only `@font-face` in `index.html`:
  ```css
  @font-face { font-family: 'NotoRef';
    src: url('/noto-ref/NotoColorEmoji-Regular.ttf') format('truetype'); }
  ```
  used **only** by a hidden reference measurement (a canvas 2D context / hidden element),
  never by the production `#parley` canvas path.
- **Keep the 25 MB font out of the app's load path and out of the trunk bundle:** do *not*
  use trunk `copy-file` (that would bake it into `dist/`). Instead have `validate.py`'s HTTP
  server expose a dedicated route `/noto-ref/NotoColorEmoji-Regular.ttf` that streams the
  file straight from the repo path. The font is thus present only during validation, served
  by the harness, not part of the app payload. Document this explicitly: the "cannot
  download the entire font" rule governs the *production* path; the validation reference is
  allowed to read the real font purely to measure.
- In the page, after `document.fonts.load("48px 'NotoRef'")` resolves, measure the full
  string with font stack `"48px 'Arimo','NotoRef'"` via `ctx.measureText(EXAMPLE_TEXT).width`
  → `noto_ref_line_width`. Emoji resolve to NotoRef (advance 1275/em), Latin to Arimo.
  Expose it in the metrics JSON.

### 6.2 Comparisons (all emitted to `#data-phase-three` JSON, checked by validate.py)
1. **Per-emoji table check:** `noto_advance_px(cp)` from the embedded table == in-page
   `measureText(emoji)` with `'NotoRef'` at FONT_SIZE. Expect exactly 59.766 px @48; tol ≤0.5 px.
2. **Line-width parity (primary acceptance):** Parley `layout.width()` == `noto_ref_line_width`
   within **≤ 1 px** (allow a little slack for Arimo hinting/rounding of the Latin runs; if
   the Latin runs differ, tighten by measuring emoji-only advance sums instead).
3. **Sanity:** the drawn emoji are visibly the Apple glyphs (color), enlarged by ~scale, and
   the total advance visibly matches the NotoRef reference row.

### 6.3 Harness
Copy `phase_two/validate.py`, adjust ids/paths, add the `/noto-ref/...` file-streaming route
and the reference-measurement scrape. `trunk build`; serve `dist/`; drive Chrome for Testing
(paths from PLAN.md; `--headless=new`, fall back to headed for system color emoji as in
phase_one/two); poll `#status`==`done`; scrape JSON; `GET /screenshot` →
`_artifacts/phase_three.png`.

### Acceptance criteria
1. `trunk build` succeeds on wasm32; `cargo clippy` clean (workspace lints) for both the app
   and `noto_advance_gen`.
2. Generator produces `src/noto_advances.rs` with `NOTO_UPEM = 1024` and ~1499 entries;
   `😀`/`🎉` = 1275.
3. Page reaches `done` in Chrome for Testing.
4. Per-emoji advance from embedded table matches real-Noto `measureText` (≤0.5 px).
5. Parley line width matches real-Noto reference line width (≤1 px).
6. Screenshot shows scaled Apple emoji at Noto advances; embedded payload contains no Apple
   font and no full Noto font (grep `dist/`); full Noto only served by the harness route.
7. No Parley library changes; only uncommitted new files + root `members` edit. Nothing committed.

## 8. Risks / open questions

- **R1 — Which font wins for emoji in the reference stack.** With `'Arimo','NotoRef'`, the
  browser must pick NotoRef (not system Apple emoji) for the emoji codepoints. NotoRef covers
  them, and being explicitly in the stack it should be chosen; verify in the scrape (per-emoji
  check #1 catches it: Apple advance ≠ 59.77). Mitigation: measure emoji individually with an
  emoji-only NotoRef stack if the mixed stack misbehaves.
- **R2 — skrifa 0.43 API surface.** Exact names for charmap/hmtx/head may differ slightly;
  resolve at implementation time (read-fonts `TableProvider` is the fallback for raw hmtx).
- **R3 — Latin-run width differences** between Parley (Arimo, hinted/quantized) and browser
  `measureText` could eat into the 1 px budget independent of emoji. Mitigation: primary
  check on **emoji advance sum** (table vs NotoRef), with full-line parity as secondary.
- **R4 — Non-1275 / multi-scalar emoji.** Out of scope: example stays single-`char` emoji
  (both 1275). The table still lists all 1499 codepoints for generality.
- **R5 — Uniform vs axis scaling.** We scale uniformly (aspect-preserving); this changes
  vertical ink extent slightly. Baselines are out of scope, so acceptable; noted so phase_four
  owns it.
- **R6 — 25 MB served by harness** is slow to fetch once per validation run; acceptable
  locally. Keep it off the app path.

### Open questions needing team-lead ruling
- **Q1:** Generator as a **standalone `noto_advance_gen` crate** (recommended) vs an `xtask`
  subcommand vs a `[[bin]]` in the phase_three crate. (Recommend standalone crate.)
- **Q2:** Data-file format — **generated `.rs` slice** (recommended, zero runtime download)
  vs `include_bytes!` binary blob vs JSON.
- **Q3:** Confirm serving the full NotoColorEmoji-Regular.ttf via the **validate.py harness
  route** (not trunk/dist) for the reference is the intended reading of "validation reference
  may use the full font, production path may not."
- **Q4:** Primary acceptance metric — **emoji-advance-sum parity** vs full-line-width parity
  (recommend emoji-sum primary, full-line secondary, both ≤1 px).
- **Q5:** Store full 1499-entry table (recommended, simple) vs exceptions-only (<1 KB).
